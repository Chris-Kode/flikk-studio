# Key decisions

| Topic | Decision | Why |
| --- | --- | --- |
| Time | `Time(i64)` in flicks (1/705 600 000 s). `TimeRange` is half-open. | It is exact for each common frame rate and sample rate. Long timelines have no drift. |
| IDs | UUID v4 newtypes. `Display` prints 8 hex chars. | They are stable across save/load. They are safe to show in chat (`@clip 3f2a91c0`). |
| Model | One timeline for each project. Flikk does not have nested sequences / compound clips. | The bus stays simple. |
| Format | `SequenceSettings` sets the frame size from the aspect (`Format::ALL`: 16:9, 9:16, 1:1, 4:5, 21:9, 4:3) and the short side (720p–4K). The undoable `SetFormat` changes it. | One project can be landscape, vertical or square. Presets and lettering follow the short side. |
| Captions | Clips on `TrackKind::Caption` tracks, with times for each word. | Ripple, move and undo change the caption times with no extra work (C3). Highlights follow the speech. |
| Protected ranges | `Marker { kind: Protected }`. Cut planners add `Warning::TouchesProtected`. | The bus enforces F4 for hand edits and agent edits equally. |
| FFmpeg | Start the `ffmpeg`/`ffprobe` binaries. The sequence of search is: `FLIKK_FFMPEG` / `FLIKK_FFPROBE`, then the copy that the release packages put adjacent to the editor, then `PATH`. | No libav linking on Windows/macOS. |
| Playback | On import, the code makes a 720p proxy (`cache/proxies/<fp>.mp4`). Playback uses the proxy when it exists. Streams send RGBA through a pipe from a long-lived ffmpeg (`-hwaccel auto`, software fallback). The GPU composes the frames, and the UI paints them as images. | Smooth playback on a laptop without a GPU video surface. |
| Fingerprint | BLAKE3 over the file size, the head, the tail and 8 evenly spaced 1 MiB chunks. For a file under 10 MiB, it uses the whole file. | It is fast on multi-GB files. It is sufficient to find a replaced file (F2). |
| Compositor | One `flikk_core::compose::program` draws the frame for the viewer, for the views of the agent and for composited render ranges. | The preview is the same as the export. |
| Whisper | `whisper-rs` (whisper.cpp), with the ggml model in `paths::models()`. It runs on the GPU (Metal on macOS, Vulkan on Windows and Linux), else on the CPU. | It is local, gives word timestamps and accepts any language. Each use has no cost. |
| Word times | Forced alignment of the Whisper words with Qwen3-ForcedAligner-0.6B (Apache-2.0). We made the ONNX export, with 4-bit weights, 589 MB. It runs on ONNX Runtime (`ort`, linked statically at build time). | In conversation, the Whisper word times drift by a maximum of one second. On hand-labelled English, the aligner puts 94 % of word starts within 100 ms (Whisper: 48 %). One model with a permissive license covers 11 languages. |
| Hearing | The model never hears audio. Analysis changes the audio into the sound script: words, `[sounds]`, `♪` music with tempo and changes, and silences. Analysis also makes beats for cuts, vectors for search by description, and spectrogram pictures. | The two backends do not accept audio input. Models put sounds in time much less accurately than text. The transcript and collages already work in this way. |
| Sounds | EfficientAT mn10_as (MIT; 527 AudioSet classes) on 2 s windows, one each second. Each window has 4 s of silence after it. The code groups the classes into approximately 180 names for the script. | It is small (20 MB) and fast on the CPU. The model learned on 10 s clips, so a 2 s window alone gives nonsense answers. With 6 s, nine in ten answers are the same as the 10 s answers, at half the cost. |
| Beats | Beat This! `final0` (MIT) on each part of music, in 30 s chunks, with its own minimal peak picking. | It is state of the art for beats and downbeats without a DBN. It runs only where the tagger heard music. |
| Sound search | LAION's larger_clap_general (Apache-2.0). It makes one vector for each 4 s window, every 2 s, in int8, in `<fp>.vectors`. At query time, the text tower encodes a description. | It finds sounds that are not in the vocabulary of the tagger ("sizzling bacon"). It also finds sounds that are like an example. Each 2 s step gets the lower score of its two windows, so a sound has a position accurate to approximately 2 s. |
| Caches | The key of derived media data is the fingerprint, under `paths::cache()`. | When the user opens a project again, the code never calculates the data again (principle 4, V6). |
| Agent ↔ editor | The backend CLI starts an MCP server over stdio. The server connects to the editor over `127.0.0.1:<port>` with a token. The editor answers calls in `AgentLink::pump` on the UI thread. | One code path for Windows and macOS. The bus stays single-threaded. |
| Tool schema | Times in tool arguments are seconds, `"M:SS.mmm"`, `"H:MM:SS.s"`, timecode `"HH:MM:SS:FF"`, frames `"f:1234"` or `@time`/`@range`. Results are seconds to the millisecond. | Models read and write these formats reliably. |
| Persistence | Projects are `.flikk` files. They are versioned JSON with atomic writes. Each media path is absolute and also relative to the file. The files go where the user selects. Unsaved changes autosave to `paths::autosave()`. Saved files get timed copies in `paths::backups()`. Undo history and pending change sets stay only for the session. User data is SQLite (WAL) at `paths::database()`. | Projects move between folders and machines, as in each professional editor. Each user has one database. |
| Library | The library is under `paths::library()`, and each project shares it (`flikk-core::library`). It contains FX programs (`.flikkfx`), presets, sounds and voices. Presets (`.flikkpreset`) are effects, audio effects or a grade, with their values. Sounds have the extension `.flikksound`. Their audio is in `paths::assets()`, `library/assets/`, with a folder for each content. A voice file (`.flikkvoice`) has the voice id of the provider and how the voice was made. It also has the stability and similarity at which the voice reads best, and a sample under `paths::assets()/voices/`. A voice is on the account of the provider. Its file lists the voice, plays it and makes it again without a request. When the user uses a program, the code copies it into the project with its `origin`. Presets contain the project programs that they use. When the user uses a sound, the code adds a media item on its file to the Library bin of the pool. When the user removes a sound, the audio stays. When the user adds sounds without results, and on launch, analysis examines them. It examines only sounds, music, beats and vectors (`AnalysisService::analyze_sound`). Thus no data goes to a provider. | A `.flikk` file stays complete at any location. Library edits go to a project only when the user updates the copy in the project. Audio is too large to copy into each project. A project that uses the audio must not go offline. |
| User data | Only under `paths::home()` (`$FLIKK_HOME` or `~/.flikk`). Project files and exports go where the user saves them. | AGENTS.md hard rule 2. |
| Online providers | `flikk-cloud` has a catalog of providers. Each provider is a folder with its client behind `Api`. The folder also has the capabilities that the provider supplies, and on which models. The capabilities (`Capability`) are transcription, music, sound effects, voiceover, video, image and upscale. The user selects one provider for each capability in Settings → Integrations (`CloudSettings`, for each user in the store). No work runs online unless the user selects it. By default, transcription stays local. | A new provider or capability is a catalog entry. Settings, analysis and the agent find it there. |
| API keys | In the credential store of the system (Keychain, Credential Manager, Secret Service; `keyring`), under the service "flikk". If the system has no credential store, an owner-only `credentials.json` in `paths::home()`. The environment variable of a provider (`ELEVENLABS_API_KEY`, `FAL_KEY`, `PIKA_API_KEY`) has priority. | Never in the database, in `.flikk` files or in logs. |
| GPU work | GPU work takes turns through `flikk_os::gpu`. Each turn is one frame or one inference. Work that the user watches never waits. The Jobs list in the title bar shows the work that takes turns ([spec](gpu-turns.md)). | The GPU users are on different APIs. Thus only the CPU side can divide the GPU time. A job that takes turns is in the list automatically. |
| Blockout renderer | The CPU ray tracer, ported to WGSL compute on the device of the effects engine. The CPU renderer stays as the reference and the fallback ([spec](blockout-gpu.md)). | The picture is the same. The preview is full-size and clips are faster. A machine without a GPU loses nothing. |
| Speed ramps | Speed keys on clip time, with straight lines between them. Source time is their integral. The code solves it in closed form in the two directions (`flikk-core/src/speed.rs`). The `speed` of a ramped clip is its mean. | It is exact after trims and splits. A cut adds a key, and the shape does not change. Each timeline → source mapping goes through `Clip::to_source` / `source_offset`. |
| Slow motion | For each clip, one of three methods: frame repeat, blend or optical flow. Blend mixes two adjacent source frames in the batch. Optical flow uses RIFE v4 (MIT) in the ONNX export of FuryTMP. In this export, the time step is an input. The export is pinned and is 22 MB. It runs on ONNX Runtime, on the GPU (`onnx::GpuSessions`). The code makes flow frames off the UI thread. Until they arrive, the code uses blended frames. Renders wait for each flow frame. | One run makes the frame at any time between two frames. Blending keeps playback smooth while the CPU is not yet at the same position. After the code makes the frames, the render is the same as the viewer. |
| Person masks | MODNet (Apache-2.0; the ONNX export of Xenova, pinned), for each frame, at a short side of 512. A guided filter puts the edge smoothly onto the full-size frame. Where the edge almost did not change, the code moves it smoothly toward the frame before. The code keeps mattes by fingerprint and model, and makes them before the playhead arrives. | One click, with no prompt and no green screen. A matting model gives soft hair, but a segmenter gives a hard edge. It is fast enough to run before playback. SAM 2 stays for objects and for one person in a group. Its license (GPL-3.0) excluded Robust Video Matting. |
| Depth maps | Depth Anything V2 Small (Apache-2.0; the ONNX export of onnx-community, pinned) on ONNX Runtime. It runs on each source frame at 518 on the longer side. The code spreads the values over the 2nd–98th percentile of each frame and smooths them over ±2 frames. It keeps them by fingerprint and model. Effects read the depth as `getDepth(uv)`. | One model with a permissive license gives relative depth for any picture. Effects must know which item is in front of which item. They do not need metres. The larger sizes are CC-BY-NC. |
| Subject masks | SAM 2.1 tiny (Apache-2.0). On macOS, the code is written over MLX (`mlx-rs`) and runs on the GPU. On other systems, it runs as five ONNX graphs (the video export of square-zero-labs, pinned). Rust assembles the memory bank as the `Sam2VideoModel` of `transformers` does. Prompts are on source frames. The code keeps mattes (the 256² logits of the model) by fingerprint, prompts and model. | Clicks and a box tell *which* object, and the model finds its edge. This is the same for the user and the agent. Tracking follows the object through occlusion. The two runtimes use the same weights. We compared one runtime with PyTorch, and the other runtime with the first. |

Before you use CLI flags, compare them with the installed `claude --help`
and with the current Codex docs (PRD note).
